# Making YardHarvest bilingual

Spanish, English, and the machinery underneath both. This describes **P0** —
the foundations — which is deployed and deliberately invisible: every string
still renders in English, and the language picker does not appear until
`SPANISH_ENABLED` is set.

## The one rule

**A message is written in its recipient's language, not in the language of
whoever triggered it.**

An organizer clicking "send dues reminders" is one request, in English,
producing forty emails in whatever language each member chose. Anything that
composes a message *for somebody else* belongs inside `force_locale`:

```python
from app.i18n import force_locale

with force_locale(member):
    subject, html = build_dues_reminder(garden, member)
send_email(member.email, subject, html)
```

Without it the failure is silent, and it is visible only to the person least
able to report it: they ticked the box, they believe they are subscribed, and
everything arrives in a language they did not pick.

## How the language is decided

### On the server (`app/i18n.py`)

Highest first:

1. `/es/…` in the path — the URL is the most explicit statement of intent
   there is, it is what a shared link carries, and it is what the crawler sees.
2. The signed-in user's `User.language`.
3. The `yh_lang` cookie (a signed-out reader's choice).
4. `Accept-Language`.
5. English.

`force_locale` overrides all of it, because the request context is not the
audience.

### On the client (`frontend/src/i18n/index.js`)

The URL, and nothing else. If the client inferred the language from a cookie
while the server rendered from the path, the two would disagree on exactly the
pages people share.

Switching language is therefore a real navigation, not a state update. That
costs one page load and buys a URL that means the same thing to whoever opens
it next.

## URLs

English keeps today's URLs. Spanish is prefixed:

| English | Spanish |
| --- | --- |
| `/pricing` | `/es/pricing` |
| `/` | `/es` |

The site is indexed, so moving English to `/en/` would break every existing
link for no gain.

None of the 74 routes or any `<Link>` needed editing: `<BrowserRouter
basename>` is set to `/es` inside a Spanish session, and React Router resolves
every relative path against it.

## Adding a translatable string

### Python

```python
from flask_babel import gettext as _
return jsonify({'error': _('Plot is already taken')}), 409
```

The SPA prints `error` verbatim in ~24 places, so wrapping the string is the
entire change at this end — no error codes, no edits at the render sites.

Then:

```bash
.venv/Scripts/python.exe -m babel.messages.frontend extract -F babel.cfg -o translations/messages.pot --project=YardHarvest --no-location .
.venv/Scripts/python.exe -m babel.messages.frontend update -i translations/messages.pot -d translations
# ... translate translations/es/LC_MESSAGES/messages.po ...
.venv/Scripts/python.exe -m babel.messages.frontend compile -d translations
```

The compiled `.mo` files are committed: the deploy runs `build.sh`, which does
not compile catalogs.

### React

```jsx
const { t } = useTranslation();
<h1>{t('plots.title')}</h1>
```

Catalogs live in `frontend/src/i18n/locales/<lang>/common.json`. A missing
Spanish string falls back to English rather than rendering the key — half
translated is the normal state for a while, and `plots.title` on screen is the
wrong way to show it.

**Never concatenate.** Spanish does not keep English's word order, and a
sentence glued together from fragments cannot be reordered by a translator:

```jsx
t('plots.assigned', { name: plot.label })   // yes
`Plot ${plot.label} assigned`               // no
```

Sentences containing markup (a `<Link>`, a `<strong>`) need `<Trans>`. There
are 181 of them and they are the ones that blow estimates — they look like one
string and are really three.

## Progress

**P1a — the auth and account flow is translated** (7 files, 114 keys): sign in,
register, forgot/reset password, notification preferences, the 404, and the SMS
consent disclosure. A Spanish speaker can create an account and sign in without
meeting English.

Two vocabulary decisions worth keeping:

- **A garden is a `huerto`, not a `jardín`.** Jardín is ornamental; huerto is
  where food grows. Getting this wrong makes the whole product read as though
  it were about flowerbeds.
- **STOP and HELP stay in English** in the SMS disclosure. They are keywords
  the carrier matches on, not words. A translated STOP unsubscribes nobody.

**P1b — `GardenDetail.jsx`, the core member screen** (~200 strings). All seven
tabs render in Spanish; English is unchanged except that "Operating Model" now
reads "Individual plots" rather than a capitalised `allotment`.

Dates now follow the page language (`i18n.language`), not a hardcoded `en-US`
and not the browser: an `es` reader with a `de-DE` browser was getting German
dates on a Spanish page.

**P3b — `GardenAdminDashboard.jsx`, the organizer portal** (3,500 lines, ~600
`t()` calls) plus the two components that render inside it,
`GardenSetupChecklist` and `GardenLayoutEditor` (the Garden Designer, which was
English top to bottom inside an otherwise Spanish Plots tab). All 14 tabs.

Four non-translation bugs it turned up, all pre-existing:

- **Plot and waitlist status printed the raw database slug** — the Situación
  column read `available`, lowercase and English. Wrong in English too; a
  Spanish page is just what made it visible.
- **Expense categories and member roles** did the same (`supplies`, and
  `co organizer` from a naive `replace('_', ' ')`).
- **The announcement priority badge** printed `normal`.
- **`alt={t('dash.qrCode')}` inside the printed QR label's HTML string** — see
  Traps.

**P1c — the gardens listing** (`GardenHome.jsx`, 33 strings). This closed a
seam the earlier phases opened: a Spanish speaker was landing on an all-English
listing and clicking into a Spanish detail page.

It also ended a vocabulary drift. The listing rendered `allotment` as
"Allotment" while the detail page called it "Individual plots" — the same
garden, two words. Both now read the same `garden.modelAllotment` key.

Catalogs: **340 keys**.

**P2 (part) — the member-facing emails.** Six of them, plus the shared shell
that wraps every platform email: plot assigned, waitlisted, dues reminder,
shift reminder, shift signup, password reset.

This is where `force_locale` finally does the job it was built for. The
content is assembled **before** `send_email` is called, so the wrapper goes
around the construction, not the send:

```python
with force_locale(_recipient_language(user_email)):
    content = f'''...{_('Hi %(name)s,', name=name)}...'''
    send_email(user_email, _subject(_('...')), _render(content))
```

`_recipient_language(address)` resolves the stored preference from the
address, because these senders take an email string rather than a user. An
address with no account returns None, which changes nothing — a booking guest
still gets their mail.

**P2 (rest) — every remaining sender except five.** 20 senders now render in
their recipient's language: the member set, the ten organizer lifecycle and
trial-drip emails, and the four marketplace ones. The Spanish catalog is 199
strings.

### The decorator

Wrapping a long f-string body in `with` means re-indenting every line of HTML,
and re-indenting HTML by hand is how a closing tag goes missing. So the rule
is declared instead:

```python
@in_recipient_language(lambda garden, organizer: organizer)
def send_garden_trial_welcome(garden, organizer):
    ...
```

The resolver takes the sender's own arguments and returns a user, a language
code, or an address to look up. The six converted before this existed use an
explicit `with force_locale(...)`; the two are equivalent and the inline form
was left rather than churned.

### Bulk sends go once per language

`send_garden_announcement` and `send_event_cancelled_email` take a LIST. A
bulk send renders one body, so forty members across two languages need two
sends — and a single-language garden still takes exactly one. `_by_language()`
groups them.

The announcement's **title and body are the organizer's own words** and are
never translated; only the wrapper around them is. A Spanish member therefore
gets Spanish chrome around whatever the organizer wrote, which is honest.

### Five senders stay English, deliberately

| Sender | Why |
| --- | --- |
| `send_operator_conversion_ping` | an internal notice to the operator, not a user |
| `send_booking_*` (4) | meeting guests have no account, so no stored language |

### Two bugs translation alone would not have fixed

* `strftime('%B %d, %Y')` uses the C locale, so month names were English in
  every language. `format_date(..., format='long')` gives "15 de octubre de
  2026" instead of "October 15, 2026".
* `member{'s' if n != 1 else ''}` and `grower{'s' ...}` glued English plurals
  on with string surgery. `ngettext` lets the catalog decide, and the catalog
  carries four plural entries now.

**P3a — the organizer screens a garden owner uses**: MyGardens, CreateGarden,

`GardenAdminDashboard.jsx` is 435 strings on its own — more than twice

## Three more traps, all build-clean and runtime-broken

**A missing import.** A bulk edit inserted `useTranslation()` into
GardenBilling but not its import, because the anchor line it looked for
(`useAuth`) is not in that file and the script used `.replace()` without
asserting. The build passed — a missing import is not a compile error in JS —
and the page died on load with *"useTranslation is not defined"*.
`keys.test.js` now fails if any file uses i18n without importing it.

**A key that does not exist.** `gardensList.browseGardens` was referenced
before it was added, which renders the KEY to the reader. `keys.test.js`
checks every literal `t('...')` and `i18nKey=` against the catalog (and knows
that i18next plurals live as `key_one`/`key_other`, so a pluralised key is
not a false positive).

**gettext syntax in the i18next catalog.** `%(days)s` pasted into
`common.json` renders literally — *"prueba gratuita de %(days)s días"*
reached a browser. The server catalog uses `%(name)s`, the client uses
`{{name}}`, and mixing them is invisible to the en-vs-es comparison because
both sides are equally wrong. `catalogs.test.js` now rejects gettext-shaped
placeholders.

## Two non-translation bugs found on the way

**The billing page understated its own offer.** "Save $55 — over 3 months
free" was hardcoded from $15/$125. Production charges $12/$60, where the
annual saving is **$84 and seven months**. Both figures are now computed from
the pricing the API sends. Same rule as `app/pricing.py`: the admin console is
the only place a price lives.

**`operating_model` has two live vocabularies.** The settings form writes
`individual|collective|hybrid`; the column default and the public pages use
`allotment|communal|hybrid`. Each screen understood only one, so a garden left
on the default rendered no chip on MyGardens, and one saved through settings
showed the raw word on its public page. Both vocabularies now resolve to the
same label. Renaming the column's values is the real fix and is a migration.

Also worth knowing: the `SiteEmailConfig` column defaults are **$15 / $125**,
so a fresh database starts life advertising the wrong price until an admin
saves the real one. `seo.py`'s
server-injected titles are still English on `/es/` pages, so a crawler sees
English metadata on a Spanish page — that is P4, and the reason
`SPANISH_ENABLED` (and therefore `hreflang`) stays off.

## Fuzzy entries are machine guesses, and they are wrong

`pybabel update` fills a new msgid by copying from a similar existing one and
marking it `#, fuzzy`. The guesses are plausible and wrong. Actual output from
this phase:

| msgid | what pybabel wrote |
| --- | --- |
| `Dues reminder for %(garden)s` | *Lista de espera en %(garden)s* — "waitlist" |
| `Upcoming shift at %(garden)s` | *Te asignaron una parcela* — "you were assigned a plot" |
| `You're signed up!` | *¡Te asignaron una parcela!* |

Two of those carried a stale `%(plot)s` and broke the compile. The rest would
have **shipped silently**, telling a member the wrong thing in a language
nobody here reads fluently. Treat a fuzzy entry as untranslated;
`test_no_fuzzy_translations_ship` fails the build if any survive, and
`test_placeholders_survive_translation` catches the mismatched ones.

## Two traps when converting in bulk

**`t()` at module scope.** A blind string replacement rewrote a module-level
constant (the plot-map legend), so `t()` ran at import time with no hook in
scope. The build passed; the page died with *"Cannot read properties of
undefined (reading 'default')"* inside a lazy chunk, which names neither the
file nor the cause. Store the KEY in module-level data and translate at the
render site.

**A second component in the same file.** `GardenDetail.jsx` also defines
`DuesPaymentForm`; the script only added `useTranslation()` to the default
export, so every `t()` in the other component had no `t`. Check per component,
not per file:

```bash
# every t() call must sit in a component that calls useTranslation()
```

**Raw database values shown to the reader.** `textTransform: 'capitalize'` on
`operating_model`, `plot.status` and `resource_type` capitalises whatever the
column holds — which cannot translate. Those now look up a label
(`garden.statusAvailable`, `garden.modelAllotment`, …) with the raw value as
the fallback, so an unrecognised value degrades to what it always showed.

## The `<Trans>` index trap

`<Trans>` maps `<1>`, `<3>` onto the **children** of the JSX element, and a
`{' '}` expression container **counts as a child**:

```jsx
... and{' '}                                  // child 3 — the whitespace
<Link to="/terms">Terms of Service</Link>     // child 4, not 3
```

A catalog string saying `<3>` then renders the space and the link silently
disappears — in every language at once, so comparing English against Spanish
cannot see it. Keep the links on one line with no `{' '}` between them, and
assert the rendered output: `SmsConsentNote.test.jsx` does, in both languages.

## Five places a string hides from a ">text<" regex

This is the most useful thing the rollout turned up, and it cost four
shipped-but-still-English pages to learn. `scripts/i18n_inventory.py` answers
"how much is left across the app". It cannot answer "is this file done",
because it only matches JSX text and attributes. These five shapes are
invisible to it, and between them they account for every page that was marked
complete and then showed English on screen:

| shape | example | why the regex misses it |
| --- | --- | --- |
| **adjacent** | `>Dues Overview — {duesSeason}</h6>` | an expression on one side, so there is no complete `>text<` |
| **ternary** | `{saving ? 'Saving…' : 'Save Settings'}` | no angle bracket anywhere near it |
| **call** | `toast('Message deleted')`, `confirmDialog(…)`, `title:`/`placeholder:`/`hint=` | a JS literal, not markup |
| **fallback** | `err.response?.data?.error \|\| 'Error saving photo'` | same, and it only renders when the server said nothing |
| **entity / wrapped** | `Billing &amp; Payouts`; a paragraph the formatter broke across lines | `&amp;` is in no letters-class; no single line holds the sentence |

The **call** and **fallback** buckets matter most. They are the strings a
reader meets at the moment they act — one per button press — and the fallback
branch is the one that fires when something has already gone wrong. On
`GardenAdminDashboard` they were 92 call sites and 26 copies of a bare
`'Error'`, none of which any earlier pass had seen.

So there is a second script, which answers the per-file question:

```bash
.venv/Scripts/python.exe scripts/i18n_leftovers.py                  # whole app
.venv/Scripts/python.exe scripts/i18n_leftovers.py GardenAdmin      # one file
.venv/Scripts/python.exe scripts/i18n_leftovers.py --quiet          # counts
```

It exits non-zero when it finds anything, so it can gate a commit. It also
reports some noise — a class fragment, a data slug — which is the right
failure direction: noise you dismiss beats the confident zero the inventory
was giving.

Two things it taught about writing a detector, both of which bit me:

- **Blank comments, do not delete them.** Deleting a line renumbers every line
  after it, and the reported line number no longer matches the file.
- **A `<Trans>`'s children are the English source** for its key. Counting them
  reports a finished file as unfinished. Both scripts now blank
  `<Trans>…</Trans>` before scanning.

## Dates follow the page, not the browser

`new Date(x).toLocaleDateString()` with no locale uses the **browser's**
locale. A Spanish page in a US-English browser renders "Sep 30, 2026" under
Spanish prose, and nobody catches it in review because the reviewer's browser
agrees with the page. Passing `'en-US'` explicitly is the same bug stated out
loud — several call sites did that to force a short month name and got a
permanently English date as the side effect.

`frontend/src/i18n/dates.js` is the fix: `formatDate` / `formatDateTime` /
`formatTime` read the language from i18next, return `''` for a null or
unparseable value instead of "Invalid Date", and export the option presets
(`DAY_MONTH_YEAR`, `DAY_MONTH_TIME`, `HOUR_MINUTE`) so the short forms are
named rather than retyped.

`GardenDetail.jsx` still passes `i18n.language` inline at 12 sites. That is
correct — Intl accepts `'es'` — but it is a second idiom for one job. Migrate
it to the helpers next time that file is open.

## Turning Spanish on

Set `SPANISH_ENABLED=1` in the Render dashboard. That does three things:

- the language picker appears in the navbar;
- `/api/admin/site-config` reports `languages: ["en", "es"]`;
- `seo.py` starts emitting `hreflang`.

Leave it off until the translation is actually there. Advertising an alternate
that is still half-English invites Google to serve the Spanish URL to Spanish
searchers before there is Spanish on it — worse than advertising nothing.

`/es/` works for anyone who types it either way; the flag only controls
whether anything *points* at it.

## Traps

- **Catalog path.** Flask-Babel resolves a relative
  `BABEL_TRANSLATION_DIRECTORIES` against the app *package* (`app/`), not the
  repo root. `app/i18n.py` sets an absolute path. A mismatch fails silently —
  gettext just returns the English text.
- **Language bleed between requests.** Flask-Babel caches the resolved locale
  on `g`, which belongs to the *application* context and can outlive a single
  request. `init_app` registers a `before_request` that calls `refresh()`;
  without it the first request to touch a translated string pins the language
  for every request after it. Covered by
  `test_one_readers_language_does_not_leak_into_the_next_request`.
- **Two 404 handlers.** `app/__init__.py` registers one for SPA mode and one
  without. Mark both or the tests (which run without a `dist/`) exercise the
  unmarked one.
- **Help-centre price tokens.** Articles must never hardcode a price — they
  read `garden_pro_pricing()`. A translator will cheerfully turn `{{price}}`
  into `{{precio}}` and break it silently. Lock the tokens before handing off.
- **`seo.py` ↔ client `<Seo>`** already have a keep-in-sync contract. It now
  doubles.
- **SMS length.** Spanish runs 15–25% longer, which pushes messages past the
  160-character GSM segment boundary: more segments, more cost, and truncation
  mid-sentence.
- **Dates.** 38 files call `toLocaleDateString`/`Intl.`. Any that parse a
  formatted date back into a value will break under `es`. Use
  `frontend/src/i18n/dates.js`; see "Dates follow the page" above.
- **Tests need an i18next instance.** `src/test/setup.js` imports
  `../i18n` globally. Without it `useTranslation` returns the key and every
  assertion on the copy fails — but the useful part is the other direction:
  the English assertions already in the suite now check that the `en` catalog
  still says what the hardcoded string said, which is the half of a
  translation nobody reviews. `GardenSetupChecklist.test.jsx` passed
  unchanged after conversion, which is what proved the catalog faithful.
- **A key holding two words of a sentence is worse than no key.** Four
  paragraphs ended up half-translated because a pass lifted the one phrase it
  could match (`'Stripe holds'`, `'Finish account payout set-up'`) and left
  the connecting clauses in English. It reads as done and it fixes a clause
  order Spanish does not use. A sentence with markup in it goes in one
  `<Trans>`, and the fragment key gets deleted so nothing is rebuilt on it.
- **JSX syntax inside a string the browser will parse as HTML.** `handlePrintQR`
  builds an HTML document as a template literal and writes it to a new window.
  A pass rewrote `alt="QR code"` there to `alt={t('dash.qrCode')}` as though it
  were markup; inside a plain string it is not, so the printed label's alt text
  became the literal characters `{t('dash.qrCode')}`. It needs `${...}`,
  escaped like its neighbours.
- **A blanket accent rule will introduce errors.** Sweeping the Spanish
  catalog for unaccented words that always take an accent found two real
  misses — and "corrected" `cada quien` to `cada quién`, which is wrong.
  `quien`, `donde`, `que` and `cuando` carry an accent only in a question, so
  they must stay out of any such rule.
- **User-generated content is not translated** — garden names, plot notes,
  announcements, member messages. Say so in the UI, or a Spanish reader will
  assume the English announcement is a bug.
