# Making YardHarvest bilingual

Spanish, English, and the machinery underneath both. This describes **P0** —
the foundations — which is deployed and deliberately invisible: every string
still renders in English, and the language picker does not appear until
`SPANISH_ENABLED` is set.

## The one rule

**A message is written in its recipient's language, not in the language of
whoever triggered it.**

An organizer clicking "send dues reminders" is one request, in English,
producing forty emails in whatever language each member chose. Anything that
composes a message *for somebody else* belongs inside `force_locale`:

```python
from app.i18n import force_locale

with force_locale(member):
    subject, html = build_dues_reminder(garden, member)
send_email(member.email, subject, html)
```

Without it the failure is silent, and it is visible only to the person least
able to report it: they ticked the box, they believe they are subscribed, and
everything arrives in a language they did not pick.

## How the language is decided

### On the server (`app/i18n.py`)

Highest first:

1. `/es/…` in the path — the URL is the most explicit statement of intent
   there is, it is what a shared link carries, and it is what the crawler sees.
2. The signed-in user's `User.language`.
3. The `yh_lang` cookie (a signed-out reader's choice).
4. `Accept-Language`.
5. English.

`force_locale` overrides all of it, because the request context is not the
audience.

### On the client (`frontend/src/i18n/index.js`)

The URL, and nothing else. If the client inferred the language from a cookie
while the server rendered from the path, the two would disagree on exactly the
pages people share.

Switching language is therefore a real navigation, not a state update. That
costs one page load and buys a URL that means the same thing to whoever opens
it next.

## URLs

English keeps today's URLs. Spanish is prefixed:

| English | Spanish |
| --- | --- |
| `/pricing` | `/es/pricing` |
| `/` | `/es` |

The site is indexed, so moving English to `/en/` would break every existing
link for no gain.

None of the 74 routes or any `<Link>` needed editing: `<BrowserRouter
basename>` is set to `/es` inside a Spanish session, and React Router resolves
every relative path against it.

## Adding a translatable string

### Python

```python
from flask_babel import gettext as _
return jsonify({'error': _('Plot is already taken')}), 409
```

The SPA prints `error` verbatim in ~24 places, so wrapping the string is the
entire change at this end — no error codes, no edits at the render sites.

Then:

```bash
.venv/Scripts/python.exe -m babel.messages.frontend extract -F babel.cfg -o translations/messages.pot --project=YardHarvest --no-location .
.venv/Scripts/python.exe -m babel.messages.frontend update -i translations/messages.pot -d translations
# ... translate translations/es/LC_MESSAGES/messages.po ...
.venv/Scripts/python.exe -m babel.messages.frontend compile -d translations
```

The compiled `.mo` files are committed: the deploy runs `build.sh`, which does
not compile catalogs.

### React

```jsx
const { t } = useTranslation();
<h1>{t('plots.title')}</h1>
```

Catalogs live in `frontend/src/i18n/locales/<lang>/common.json`. A missing
Spanish string falls back to English rather than rendering the key — half
translated is the normal state for a while, and `plots.title` on screen is the
wrong way to show it.

**Never concatenate.** Spanish does not keep English's word order, and a
sentence glued together from fragments cannot be reordered by a translator:

```jsx
t('plots.assigned', { name: plot.label })   // yes
`Plot ${plot.label} assigned`               // no
```

Sentences containing markup (a `<Link>`, a `<strong>`) need `<Trans>`. There
are 181 of them and they are the ones that blow estimates — they look like one
string and are really three.

## Progress

**P1a — the auth and account flow is translated** (7 files, 114 keys): sign in,
register, forgot/reset password, notification preferences, the 404, and the SMS
consent disclosure. A Spanish speaker can create an account and sign in without
meeting English.

Two vocabulary decisions worth keeping:

- **A garden is a `huerto`, not a `jardín`.** Jardín is ornamental; huerto is
  where food grows. Getting this wrong makes the whole product read as though
  it were about flowerbeds.
- **STOP and HELP stay in English** in the SMS disclosure. They are keywords
  the carrier matches on, not words. A translated STOP unsubscribes nobody.

**P1b — `GardenDetail.jsx`, the core member screen** (~200 strings). All seven
tabs render in Spanish; English is unchanged except that "Operating Model" now
reads "Individual plots" rather than a capitalised `allotment`.

Dates now follow the page language (`i18n.language`), not a hardcoded `en-US`
and not the browser: an `es` reader with a `de-DE` browser was getting German
dates on a Spanish page.

**P1c — the gardens listing** (`GardenHome.jsx`, 33 strings). This closed a
seam the earlier phases opened: a Spanish speaker was landing on an all-English
listing and clicking into a Spanish detail page.

It also ended a vocabulary drift. The listing rendered `allotment` as
"Allotment" while the detail page called it "Individual plots" — the same
garden, two words. Both now read the same `garden.modelAllotment` key.

Catalogs: **340 keys**.

**P2 (part) — the member-facing emails.** Six of them, plus the shared shell
that wraps every platform email: plot assigned, waitlisted, dues reminder,
shift reminder, shift signup, password reset.

This is where `force_locale` finally does the job it was built for. The
content is assembled **before** `send_email` is called, so the wrapper goes
around the construction, not the send:

```python
with force_locale(_recipient_language(user_email)):
    content = f'''...{_('Hi %(name)s,', name=name)}...'''
    send_email(user_email, _subject(_('...')), _render(content))
```

`_recipient_language(address)` resolves the stored preference from the
address, because these senders take an email string rather than a user. An
address with no account returns None, which changes nothing — a booking guest
still gets their mail.

Still to do: the remaining ~22 emails (order/marketplace ones are inert while
the marketplace is off; the trial-drip and operator ones are organizer-facing),
SMS, P3 organizer + admin, P4 help centre and Spanish SEO copy. `seo.py`'s
server-injected titles are still English on `/es/` pages, so a crawler sees
English metadata on a Spanish page — that is P4, and the reason
`SPANISH_ENABLED` (and therefore `hreflang`) stays off.

## The server-side catalog workflow

```bash
.venv/Scripts/python.exe -m babel.messages.frontend update -i translations/messages.pot -d translations
# ... translate, and CLEAR EVERY FUZZY FLAG (see below) ...

```

## Fuzzy entries are machine guesses, and they are wrong

`pybabel update` fills a new msgid by copying from a similar existing one and
marking it `#, fuzzy`. The guesses are plausible and wrong. Actual output from
this phase:

| msgid | what pybabel wrote |
| --- | --- |
| `Dues reminder for %(garden)s` | *Lista de espera en %(garden)s* — "waitlist" |
| `Upcoming shift at %(garden)s` | *Te asignaron una parcela* — "you were assigned a plot" |
| `You're signed up!` | *¡Te asignaron una parcela!* |

Two of those carried a stale `%(plot)s` and broke the compile. The rest would
have **shipped silently**, telling a member the wrong thing in a language
nobody here reads fluently. Treat a fuzzy entry as untranslated;
`test_no_fuzzy_translations_ship` fails the build if any survive, and
`test_placeholders_survive_translation` catches the mismatched ones.

## Two traps when converting in bulk

**`t()` at module scope.** A blind string replacement rewrote a module-level
constant (the plot-map legend), so `t()` ran at import time with no hook in
scope. The build passed; the page died with *"Cannot read properties of
undefined (reading 'default')"* inside a lazy chunk, which names neither the
file nor the cause. Store the KEY in module-level data and translate at the
render site.

**A second component in the same file.** `GardenDetail.jsx` also defines
`DuesPaymentForm`; the script only added `useTranslation()` to the default
export, so every `t()` in the other component had no `t`. Check per component,
not per file:

```bash
# every t() call must sit in a component that calls useTranslation()
```

**Raw database values shown to the reader.** `textTransform: 'capitalize'` on
`operating_model`, `plot.status` and `resource_type` capitalises whatever the
column holds — which cannot translate. Those now look up a label
(`garden.statusAvailable`, `garden.modelAllotment`, …) with the raw value as
the fallback, so an unrecognised value degrades to what it always showed.

## The `<Trans>` index trap

`<Trans>` maps `<1>`, `<3>` onto the **children** of the JSX element, and a
`{' '}` expression container **counts as a child**:

```jsx
... and{' '}                                  // child 3 — the whitespace
<Link to="/terms">Terms of Service</Link>     // child 4, not 3
```

A catalog string saying `<3>` then renders the space and the link silently
disappears — in every language at once, so comparing English against Spanish
cannot see it. Keep the links on one line with no `{' '}` between them, and
assert the rendered output: `SmsConsentNote.test.jsx` does, in both languages.

## Turning Spanish on

Set `SPANISH_ENABLED=1` in the Render dashboard. That does three things:

- the language picker appears in the navbar;
- `/api/admin/site-config` reports `languages: ["en", "es"]`;
- `seo.py` starts emitting `hreflang`.

Leave it off until the translation is actually there. Advertising an alternate
that is still half-English invites Google to serve the Spanish URL to Spanish
searchers before there is Spanish on it — worse than advertising nothing.

`/es/` works for anyone who types it either way; the flag only controls
whether anything *points* at it.

## Traps

- **Catalog path.** Flask-Babel resolves a relative
  `BABEL_TRANSLATION_DIRECTORIES` against the app *package* (`app/`), not the
  repo root. `app/i18n.py` sets an absolute path. A mismatch fails silently —
  gettext just returns the English text.
- **Language bleed between requests.** Flask-Babel caches the resolved locale
  on `g`, which belongs to the *application* context and can outlive a single
  request. `init_app` registers a `before_request` that calls `refresh()`;
  without it the first request to touch a translated string pins the language
  for every request after it. Covered by
  `test_one_readers_language_does_not_leak_into_the_next_request`.
- **Two 404 handlers.** `app/__init__.py` registers one for SPA mode and one
  without. Mark both or the tests (which run without a `dist/`) exercise the
  unmarked one.
- **Help-centre price tokens.** Articles must never hardcode a price — they
  read `garden_pro_pricing()`. A translator will cheerfully turn `{{price}}`
  into `{{precio}}` and break it silently. Lock the tokens before handing off.
- **`seo.py` ↔ client `<Seo>`** already have a keep-in-sync contract. It now
  doubles.
- **SMS length.** Spanish runs 15–25% longer, which pushes messages past the
  160-character GSM segment boundary: more segments, more cost, and truncation
  mid-sentence.
- **Dates.** 38 files call `toLocaleDateString`/`Intl.`. Any that parse a
  formatted date back into a value will break under `es`.
- **User-generated content is not translated** — garden names, plot notes,
  announcements, member messages. Say so in the UI, or a Spanish reader will
  assume the English announcement is a bug.
